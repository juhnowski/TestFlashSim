# Функциональная спецификация аппаратного интерфейса управления контроллера NVMe ZNS SSD (FPGA/RTL Level)

## Обзор
Функциональная спецификация на аппаратный интерфейс управления ZNS SSD контроллером должна быть использована как техническое задание (ТЗ) для проектирования RTL-блоков в LiteX.

Спецификация сопровождается тестами проекта (Golden Mode), как для проверки функционала в FlashSim симуляторе, так и для  верификации реального RTL-кода в железе (через Hardware-in-the-Loop или Verilator).

Чтобы реализовать этот подход, аппаратный интерфейс железного ZNS SSD (который будет синтезироваться в FPGA через LiteX/Verilog) должен иметь точно такое же отображение регистров и команд, какое заложено в метод direct_zns_gate(lba, is_write).

## 1. Архитектура и структура шины (Axi-Lite CSR Register Map)
Интерфейс управления контроллером реализуется в виде блока регистров состояния и управления (CSR), подключенных к системной шине процессора хоста (например, через сгенерированный *LiteX* интерконнект *AXI-Lite* или *Wishbone*).

Хост взаимодействует с аппаратным контроллером исключительно через запись LBA и кода операции в строго определенные порты памяти (Memory-Mapped I/O).

### 1.1. Карта аппаратных регистров контроллера
Base Address: 0x4000_0000

| Смещение (Offset) | Имя регистра | Направление | Размер | Описание |
| :--- | :--- | :--- | :--- | :--- |
| **`0x00`** | `ZNS_REG_LBA_LOW` | Write-Only | 32-bit | Младшие 32 бита целевого логического адреса (LBA). |
| **`0x04`** | `ZNS_REG_LBA_HIGH` | Write-Only | 32-bit | Старшие 32 бита целевого логического адреса (LBA). |
| **`0x08`** | `ZNS_REG_CMD` | Write-Only | 8-bit | Код команды (0 — Чтение, 1 — Запись, 2 — Сброс зоны). |
| **`0x0C`** | `ZNS_REG_TRIGGER` | Write-Only | 1-bit | Запись `1` инициирует исполнение команды аппаратным автоматом. |
| **`0x10`** | `ZNS_REG_STATUS` | Read-Only | 8-bit | Статус выполнения (0 — READY/SUCCESS, 1 — FAILURE/ERROR, 2 — BUSY). |
| **`0x14`** | `ZNS_REG_ERR_CODE`| Read-Only | 8-bit | Код аппаратной ошибки ZNS/Криптографии (подробное описание в п. 3). |

## 2. Аппаратный конечный автомат верификации (RTL State Machine)
Внутри FPGA за логику валидации отвечает изолированный аппаратный блок, работающий на частоте системной шины (`sys_clk`). Контроллер хранит внутреннюю BRAM-таблицу метаданных для всех 4096 зон (входной адрес BRAM: `zone_id = LBA >> 6`). 
Для каждой зоны в ячейке памяти хранятся: 
```
[6-bit wptr | 1-bit is_full | 16-bit erase_count]
```
### 2.1 Порядок обработки транзакции аппаратным автоматом:
1. Хост записывает адрес в `ZNS_REG_LBA` и код в `ZNS_REG_CMD`.
2. Хост взводит триггер `ZNS_REG_TRIGGER = 1`. Контроллер переходит в состояние BUSY.
3. Аппаратный валидатор вычисляет `zone_id` и `target_page` сдвигом и маской:
  - `zone_id <= LBA[17:6];` (деление на 64 страницы)
  - `target_page <= LBA[5:0];` (остаток от деления на 64)
4. Контроллер производит чтение метаданных зоны из BRAM за 1 такт и выполняет аппаратную проверку условий (согласно матрице тестов).
5. Если проверка пройдена: активируется линия управления физическим флеш-интерфейсом (или крипто-движком), `ZNS_REG_STATUS` выставляется в `0 (SUCCESS)`.
6. Если условия нарушены: взводится флаг прерывания, в `ZNS_REG_STATUS` пишется `1 (FAILURE)`, а операция блокируется на уровне транзисторных затворов.

## 3. Спецификация аппаратных ответов
Чтобы 9 тестов из симулятора без изменений проверяли реальное железо, RTL-контроллер при чтении регистра ZNS_REG_ERR_CODE должен возвращать строго определенные аппаратные коды ошибок:
- `0x01` (ERR_UNALIGNED_WRITE / OUT_OF_ORDER): Нарушен закон последовательной записи. Попытка записи мимо текущего wptr зоны. (Триггер для Теста 2).
- `0x02` (ERR_ZONE_RESOURCES_EXCEEDED): Превышен лимит параллельно открытых зон. Попытка перевести 5-ю зону в состояние OPEN (внутри FPGA-контроллера сработал счетчик активных зон open_zones > 4). (Триггер для Теста 4).
- `0x03` (ERR_READ_EMPTY_ZONE / BEYOND_WPTR): Запрос чтения страницы, адрес которой target_page >= wptr целевой зоны. Аппаратный мультиплексор блокирует чтение из ячеек флеша и выдает нули. (Триггер для Теста 5).
- `0x04` (ERR_KEY_DESTROYED / RING_2_GUARD): Сигнал тревоги уничтожил ключ шифрования AES-XTS. Зона аппаратно изолирована до следующего цикла Crypto-Erase. Попытка чтения вызывает отказ. (Триггер для Теста 6).
- `0x05` (WARN_WEAR_LIMIT_EXCEEDED): Счетчик стираний ячеек памяти в BRAM `erase_count >= 5`. Включается линия аппаратной защиты от деградации кремния. (Триггер для Теста 7).
- `0x06` (ERR_INVALID_CMD_ALIGNMENT): В регистр ZNS_REG_CMD записан неизвестный или невыровненный код операции (например, 99). Контроллер сбрасывает транзакцию по таймауту. (Триггер для Теста 8).
- `0x07` (ERR_WRITE_TO_FULL_ZONE): Попытка записи в зону, у которой бит is_full == 1. Блокировка переполнения физического блока памяти. (Триггер для Теста 9).

## 4. Спецификация интеграции крипто-движка (Zero-Trust Storage)
### 4.1 AES-XTS-256 Движок
Включается в конвейер между буфером ввода-вывода (AXI Stream) и контроллером физического уровня флеш-памяти (ONFI/Toggle интерфейс). Шифрование/расшифрование происходит за фиксированное количество тактов (например, 14 тактов для конвейерного AES).

### 4.2 Аппаратный сброс ключа (Crypto-Erase)
Входной пин crypto_clear или запись команды `2` сбрасывает регистры текущего ключа в ноль (`key <= 256'b0;`) по переднему фронту тактового сигнала (`posedge sys_clk`). Метаданные зоны в BRAM обнуляются. Процедура занимает ровно 1 такт процессора, обеспечивая мгновенное уничтожение информации в случае атаки Intel ME (Ring -2) через DMA.

## 5. HIL Верификация
Для запуска проверочных 9 тестов для контроллера в LiteX необходимо подменить кодовую базу метода direct_zns_gate в файле ssd_controller.cpp. Вместо FlashSim симуляции этот метод будет физически записывать данные в порты вашей FPGA через указатели в памяти:
```cpp
// Пример того, как метод симулятора direct_zns_gate превращается в драйвер верификации железа:
enum status Controller::direct_zns_gate(unsigned long lba, int is_write)
{
    // Адрес портов управления вашей FPGA платы (указывается через mmap)
    volatile uint32_t* zns_base = (volatile uint32_t*)0x40000000; 
    
    // 1. Записываем параметры в физические CSR-регистры FPGA
    zns_base[0] = (uint32_t)(lba & 0xFFFFFFFF); // ZNS_REG_LBA_LOW
    zns_base[1] = (uint32_t)((lba >> 32) & 0xFFFFFFFF); // ZNS_REG_LBA_HIGH
    zns_base[2] = (uint32_t)is_write; // ZNS_REG_CMD
    
    // 2. Взводим триггер исполнения аппаратного автомата
    zns_base[3] = 1; // ZNS_REG_TRIGGER
    
    // 3. Опрашиваем статус завершения операции контроллером (Polling)
    while (zns_base[4] == 2) { /* Ждем, пока статус BUSY */ }
    
    // 4. Возвращаем результат SUCCESS или FAILURE на основе ответа железа
    if (zns_base[4] == 0) return SUCCESS;
    
    // Если произошел аппаратный отказ — выводим код ошибки из регистра ZNS_REG_ERR_CODE
    uint8_t err_code = zns_base[5];
    fprintf(stderr, "   [FPGA HARDWARE REFUSAL]: Аппаратный отказ с кодом 0x%02X\n", err_code);
    return FAILURE;
}
```

## 6. Техническое описание аппаратных возможностей контроллера (Hardware Features)

Разрабатываемый RTL-контроллер ZNS SSD должен обладать следующим набором встроенных аппаратных фич и модулей верификации, обеспечивающих аппаратную изоляцию и нулевую задержку при валидации команд хоста.

### 6.1. Аппаратный трекер указателей записи (Hardware Zone Tracker)
* **Архитектура на базе Dual-Port BRAM:** Контроллер не использует внешнюю DRAM хоста для хранения карты зон. Все метаданные 4096 зон хранятся внутри встроенной блочной памяти FPGA (Block RAM). Чтение текущего состояния `wptr` и бита `is_full` происходит за 1 такт тактовой частоты `sys_clk`.
* **Автономный инкремент указателя (Auto-Increment Engine):** При успешном прохождении валидации записи (`is_write == 1`), аппаратный сумматор внутри FPGA увеличивает значение `wptr` на единицу и автоматически выставляет флаг `is_full = 1`, как только `wptr` достигает значения `64` (размер зоны). Хост полностью освобожден от необходимости ручного обновления состояния регистров диска.
* **Аппаратный ограничитель ресурсов (Active Resources Limiter):** Встроенный комбинаторный счетчик в режиме реального времени подсчитывает количество зон, находящихся в состоянии `OPEN` (где `wptr > 0` и `is_full == 0`). При попытке хоста инициировать запись в 5-ю по счету зону, компаратор мгновенно блокирует транзакцию до тех пор, пока хост не переведет одну из активных зон в состояние `FULL` или не выполнит команду `Zone Reset`.

### 6.2. Модуль защиты от Ring -2 компрометации (Ring -2 DMA Anti-Exploit)
* **On-The-Fly Крипто-Движок (AES-XTS-256):** Модуль шифрования интегрирован непосредственно в конвейер записи/чтения данных между шиной PCIe (через AXI Stream) и физическим контроллером флеш-памяти. Шифрование происходит аппаратно «на лету». Хост-система (включая Ring 0, Ring -1/Гипервизор и Ring -2/Intel ME) никогда не имеет доступа к открытому тексту данных, хранящемуся в кремниевых структурах NAND.
* **Мгновенный аппаратный сброс ключей (Zero-Delay Crypto-Erase):** Контроллер оснащен выделенной линией физического сброса `crypto_clear`, подключенной к внутренним датчикам вскрытия периметра или регистру экстренной команды хоста (`ZNS_REG_CMD == 2`). При активации линии, FPGA-регистры, хранящие 256-битный ключ шифрования AES, обнуляются жесткой аппаратной логикой **ровно за 1 такт частоты**. Данные на диске мгновенно и безвозвратно превращаются в белый шум, блокируя любые попытки кражи информации со стороны скомпрометированного Intel ME через DMA-доступ.
* **Конвейерная проверка целостности данных (Hardware GMAC Signer):** При записи данных каждая страница флеш-памяти снабжается аппаратно вычисленной криптографической подписью (кодом аутентификации). При чтении (`is_write == 0`) крипто-движок сверяет подпись. Если Ring -2 или вредоносный софт попытались подменить данные в обход контроллера, движок фиксирует нарушение целостности, блокирует выдачу данных хосту и взводит аппаратный флаг ошибки `0x04`.

### 6.3. Модуль контроля деградации ячеек флеш-памяти (Silicon Wear Monitoring)
* **Аппаратный счетчик циклов стирания (BRAM Erase Counter):** Каждая ячейка памяти зон в BRAM содержит 16-битный счетчик `erase_count`. При подаче команды сброса зоны (`Zone Reset`), аппаратный автомат увеличивает значение счетчика для целевого блока памяти.
* **Аппаратный предохранитель износа (Silicon Degradation Fuse):** Контроллер содержит жестко заданный цифровой компаратор лимита износа (в симуляции настроен на 5 циклов для демонстрации). При достижении этого лимита, RTL-логика выставляет аппаратное предупреждение `0x05` и может превентивно заблокировать дальнейшие операции стирания для защиты от физического пробоя диэлектрика плавающего затвора ячеек NAND флеш-памяти.

### 6.4. Модуль строгой валидации транзакций (Strict Bus Alignment Verifier)
* **Аппаратная фильтрация невалидных команд (PCIe Command Sanity Check):** Входной демультиплексор командной шины осуществляет жесткую валидацию кодов операций. Любые невыровненные запросы, поврежденные пакеты шины или недопустимые коды (например, `99`) отсекаются на логическом уровне ввода-вывода. Контроллер мгновенно выставляет статус ошибки `0x06`, не допуская дестабилизации внутреннего конечного автомата FTL и предотвращая атаки типа «отказ в обслуживании» (DoS) на уровне прошивки накопителя.
* **Защита от аппаратного переполнения блоков (NAND Overflow Prevention):** Компаратор адресов проверяет состояние флага `is_full` целевой зоны до подачи напряжений на физические линии записи чипа. Если зона заблокирована флагом переполнения, попытка записи физически изолируется, исключая порчу соседних страниц в блоке памяти.
