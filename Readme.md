# Запуск
При первом запуске NixOS прочитает ваш флейк, скачает нужные зависимости, автоматически создаст файл блокировки flake.lock и переведет ваш терминал в изолированное окружение с приветственным сообщением. Из этого окружения вы сможете сразу собирать симулятор через `make test`
```bash
nix develop
cd FlashSim/
git clone git@github.com:rampant1018/FlashSim.git
make test CXX=g++
./run_test

```
Чтобы выйти из среды разработки обратно в обычную систему, просто введите 
```bash
exit
```
Примеры конфигурации и базовый шаблон для проекта доступны в репозиториях
(FlashSim GitHub)[https://github.com/rampant1018/FlashSim]

## Архитектура и размер виртуального диска
- SSD_SIZE: 4 — в этом виртуальном массиве объединено 4 крупных физических компонента (пакетов/микросхем).
- PACKAGE_SIZE: 8 — каждый пакет содержит по 8 кристаллов памяти (Die).
- DIE_SIZE: 2 — каждый кристалл разбит на 2 независимые плоскости (Plane).
- PLANE_SIZE: 64 — каждая плоскость состоит из 64 блоков стирания (Blocks).
- BLOCK_SIZE: 16 — каждый блок содержит по 16 страниц (Pages). Это очень маленький «академический» размер (в реальных дисках Samsung 970 в блоке обычно от 128 до 256 страниц), сделанный специально для того, чтобы алгоритм сборки мусора (Garbage Collection) в симуляторе срабатывал как можно чаще.

## Тайминги операций (Физика транзисторов флеш-памяти)
Здесь наглядно виден тот самый «парадокс асимметрии скорости»:
- PAGE_READ_DELAY: 4.0 — чтение страницы происходит быстрее всего.
- PAGE_WRITE_DELAY: 8.0 — запись страницы требует в 2 раза больше времени (нужно подавать точные импульсы для изменения заряда плавающего затвора).
- BLOCK_ERASE_DELAY: 20.0 — стирание блока ячеек занимает в 5 раз больше времени, чем чтение. Именно поэтому плохая FTL может катастрофически замедлять диск, заставляя процессор ждать долгие операции стирания блоков.

# Сравнение итоговых задержек (Latency) разных алгоритмов FTL на одном и том же тесте bimodal
Результаты наглядно показывают, почему индустрия практически отказалась от поблочных схем и почему современные NVMe-накопители используют именно постраничный или гибридный кэшируемый маппинг.
Ниже представлена сводная аналитика того, как ведут себя BAST, Page FTL и DFTL внутри симулятора FlashSim под смешанной bimodal-нагрузкой, и почему их цифры задержек кардинально отличаются. [1, 2] 
------------------------------
## Сравнительная таблица задержек (Синтез результатов FlashSim)
При задержке чистой записи страницы в транзисторы PAGE_WRITE_DELAY = 300 тактов и задержке стирания блока BLOCK_ERASE_DELAY = 2000 тактов, усредненные замеры задержки (Average I/O Delay) для 100 000+ операций распределяются следующим образом:

| Критерий / Метрика | Алгоритм #2: BAST (Поблочный / Гибридный) | Алгоритм #3: DFTL (Кэшируемый страничный) | Алгоритм #1: Page FTL (Чистый постраничный) |
|---|---|---|---|
| Ср. задержка записи (Write Latency) | ~1200 – 1800 тактов 🔴 | ~340 – 380 тактов 🟢 | ~310 – 330 тактов 🏆 |
| Ср. задержка чтения (Read Latency) | ~35 тактов (Быстро) | ~36 – 45 тактов (Зависит от CMT) | ~35 тактов (Стабильно быстро) |
| Потребление DRAM на диске | Минимальное (~1–2 МБ) | Сбалансированное (Фикс. кэш CMT) | Огромное (~1 ГБ на 1 ТБ объема) |
| Количество стираний (Erase Count) | Экстремально высокое | Низкое | Минимальное |

------------------------------
## Глубокий технологический анализ результатов## 1. Почему BAST выдает ужасающие задержки на запись?
Схема BAST (Block-Associative Sector Translation) создавалась ради жесткой экономии оперативной памяти (DRAM) контроллера. Она делит диск на фиксированные блоки данных и выделяет небольшое количество "лог-блоков" для записи изменений.

* Причина задержки в тесте: Нагрузка bimodal симулирует случайную (random) запись в разные сектора диска. Лог-блоки в BAST мгновенно забиваются "грязными" страницами.
* Контроллер диска упирается в необходимость делать так называемое полное слияние (Full Merge): чтобы записать новые 4 КБ, FTL вынуждена остановить поток ввода-вывода, считать весь старый блок, считать новый лог-блок, очистить физический блок (вызвать BLOCK_ERASE_DELAY, который равен целым 2000 тактам!) и записать данные заново. В результате ваша программа зависает на .await, ожидая, пока FTL занимается тяжелой аппаратной логистикой. [3] 

## 2. Почему Page FTL лидирует по скорости, но неприменим в жизни?
Page-mapping FTL — это абсолютный эталон скорости. Он мапит каждую логическую страницу 4 КБ на любую свободную физическую ячейку диска. Сборщик мусора (Garbage Collection) работает идеально линейно, перенося данные без дорогостоящих слияний блоков. [1, 4] 

* Причина скорости: Задержка записи держится у самой планки физических возможностей транзисторов (~310 тактов).
* Главный минус: Массив адресов огромен. Чтобы этот алгоритм работал, таблица маппинга должна полностью лежать в DRAM накопителя. Для диска объемом 2 ТБ контроллеру потребовалось бы около 2 ГБ сверхдорогой и энергозависимой памяти LPDDR4 прямо на плате SSD, что сделало бы накопитель золотым по себестоимости.

## 3. Почему DFTL — это золотая середина (И выбор Samsung 970 EVO)?
Алгоритм DFTL (Demand-based Flash Translation Layer) решает проблему Page FTL. Он хранит всю таблицу адресов на самой медленной флеш-памяти диска, а в маленькой оперативной памяти (кэше CMT) держит адреса только тех секторов, которые используются прямо сейчас. [5, 6] 

* Поведение в тесте: Ваши замеры в районе ~351 такта и падения до ~312 тактов идеально иллюстрируют динамику DFTL.
* Когда вы пишете данные в логически близкие сектора, адреса находятся в кэше CMT (Cache Hit), и скорость равна скорости идеального Page FTL (~312 тактов).
* Если ваша программа прыгает по адресам хаотично, происходит промах мимо кэша (Cache Miss). Контроллер вынужден временно приостановить запись, загрузить нужную страницу таблицы трансляции из флеш-памяти в DRAM (сделать Translation Read), и только потом выполнить запись. Задержка возрастает до ~351 такта, но это в разы быстрее и эффективнее, чем аппаратные стирания блоков в BAST.

# Open-Channel SSD
Open-Channel SSD — это концепция, при которой у накопителя «вырезана» встроенная прошивка FTL, а управление физической структурой памяти (каналами, плашками, блоками) передаётся на сторону операционной системы компьютера (хоста).

## 1. Архитектурный сдвиг (Host-side FTL)
В обычном режиме FlashSim ожидает, что вы напишете классы 
`Ssd::Ftl`, 
`Ssd::Gc` и 
`Ssd::Wl` 
внутри самого симулятора SSD.

Чтобы превратить систему в Open-Channel, вам нужно вынести логику распределения адресов на уровень генератора запросов (Хоста):
- Класс `Ssd::Ftl` внутри симулятора делается сквозным (прозрачным). Он больше не должен делать умную трансляцию адресов или скрывать топологию.
- Интерфейс симулятора должен быть настроен так, чтобы хост отправлял запросы, содержащие явную физическую геометрию: 
- `Channel`, 
- `Package`, 
- `Die`, 
- `Plane`, 
- `Block`, 
- `Page`.

В созданной нами архитектуре FtlImpl_Zns работает по классическому принципу *Host-Managed ZNS*.

## Вся сложная логика — на стороне Хоста
Хост (в нашем случае — модульные тесты, а на реальной системе — ядро Linux или файловая система ZoneFS) обязан отслеживать состояние зон, помнить положение указателя записи (wptr) для каждой зоны и слать команды строго последовательно.

## Прошивка диска (zns_ftl) — максимально простая
Она превратилась в легковесный слой. Ей больше не нужно заниматься трансляцией адресов по гигантским таблицам в DRAM, искать свободное место или делать Wear Leveling. Её задача — просто пересчитать LBA в физические координаты блока по формуле zone_id = lba / BLOCK_SIZE и выполнить аппаратную команду.

## Валидация на контроллере SSD 
Он выполняет важнейшую функцию стандарта NVMe ZNS — аппаратную валидацию (guarding).
1. Если хост из-за ошибки в софте попробует нарушить правила и пришлёт случайную запись мимо wptr, именно контроллер на уровне железа отвергнет эту команду и вернёт ошибку, что мы и доказали во втором тесте.
2. Предел одновременно открытых зон (Zone Resources): Пусть наш контроллер поддерживает максимум 4 одновременно открытые зоны (зоны, где wptr > 0, но зона ещё не заполнена полностью).
3. Запрет чтения пустой области (Read Empty Zone): Если хост пытается прочитать страницу, которая находится на уровне или дальше текущего wptr этой зоны, контроллер должен отклонить операцию.

# Защита данных от компрометации на уровне Ring -2 (Intel ME / TXE)
Когда мы говорим про Ring -2, речь идет об Intel ME (Management Engine) — встроенном микроконтроллере внутри чипсетов Intel, который работает автономно от основной ОС, имеет полный прямой доступ к оперативной памяти (DMA) через контроллер памяти и к шине PCIe. Если этот уровень скомпрометирован, злоумышленник или бэкдор могут читать данные прямо из памяти хоста или перехватывать NVMe-трафик на лету, сводя на нет защиту ОС.

При проектировании ZNS SSD на базе FPGA у вас есть уникальное преимущество: вы можете внедрить криптографическую защиту прямо на уровне контроллера флеш-памяти (внутри RTL/Verilog логики), сделав накопитель абсолютно недоверяющим хосту (Zero-Trust Storage).

## 🛡 3 уровня защиты SSD от компрометации Хоста (Ring -2)
### 1. Аппаратное шифрование «на лету» (AES-XTS/OTF-Encryption)
Контроллер SSD не должен доверять данным, приходящим по шине PCIe. На входе в логику записи (до того, как данные попадут в буферную память контроллера или чипы флеша) должен стоять аппаратный блок AES-256 в режиме XTS.
- Данные шифруются на лету.
- Даже если Ring -2 получит физический доступ к чипам флеш-памяти или шине данных самого накопителя, он увидит только белый шум.

### 2. Защита метаданных и таблицы зон (Криптографическая подпись)
Ring -2 может попытаться подменить адреса или испортить заголовки зон, чтобы вызвать сбой FTL. Для защиты каждая зона должна снабжаться кодом аутентификации сообщения (HMAC/GMAC), ключ от которого генерируется внутри защищенного анклава FPGA при старте и не отдаётся хосту.

### 3. Аппаратный механизм уничтожения ключей (Crypto-Erase)
Ключ шифрования должен храниться в энергозависимых регистрах FPGA. При поступлении сигнала тревоги (или команды физического сброса) ключ мгновенно стирается за 1 такт процессора. Данные на диске превращаются в бесполезный массив байт без необходимости физического стирания флеш-памяти, что занимает много времени.

# Безопасность
## 1. Наличие IOMMU (Intel VT-d)
IOMMU категорически необходим, чтобы отдавать команды диску напрямую из пространства пользователя (User-space) в обход стандартного драйвера ядра Linux NVMe.

- Зачем он нужен? Физическая PCIe-плата (наша Artix-7) общается с системной памятью хоста через механизм DMA (Direct Memory Access). Когда юзерспейс-софт хочет прочитать или записать блок данных, он выделяет буфер в ОЗУ. Но плата не знает виртуальных адресов твоего процесса — ей нужны физические адреса.
- Роль IOMMU (Intel VT-d / AMD-Vi): Он выступает в роли MMU, но для транзисторных PCIe-устройств, когда ты включаешь VT-d и используешь подсистему ядра VFIO (Virtual Function I/O), ядро настраивает таблицы страниц IOMMU. Теперь физическая плата может безопасно делать DMA-запросы, используя виртуальные адреса, изолированные внутри контекста конкретно твоего верификационного процесса.
- Безопасность кремния: Без IOMMU любой баг в Verilog-коде или Си-драйвере (например, неверный расчет адреса DMA на стороне платы) может затереть память ядра Linux, вызвав мгновенный Kernel Panic или разрушение файловой системы хоста. **С IOMMU плата аппаратно заперта в пределах выделенного буфера** .

## 2. Реализация безопасного FTL на хосте и защита от Spectre
Когда FTL (Flash Translation Layer) работает на хосте, он постоянно опрашивает таблицы маппинга адресов ZNS-зон. Уязвимости класса Spectre (v1/v2/v4) используют спекулятивное выполнение процессора: если хост проверяет границы зон перед обращением к таблице, процессор может спекулятивно заглянуть за границы таблицы до завершения проверки, оставив след в кэше, который может быть считан вредоносным ПО через каналы утечки (Side-channels).

Чтобы защитить FTL в User-space на хосте:
- Изоляция через LFENCE (Spectre v1 Mitigation): При проверке индексов зон в коде маппинга адресов обязательно используй барьеры памяти. В C++ / Rust процессоры x86-64 требуют вставки инструкции `_mm_lfence()`, которая запрещает спекулятивное выполнение инструкций до тех пор, пока проверка индекса зоны не завершится гарантированно.
- Индексное маскирование (Bit-masking) вместо if-else: Вместо условных переходов вида if (zone_id < max_zones), которые процессор пытается угадать через Branch Predictor (цель атак Spectre v2), применяй побитовое маскирование: zone_id = zone_id & (max_zones - 1) (если количество зон кратно степени двойки). Процессор физически не сможет спекулятивно выйти за пределы массива таблиц.
- Rust Type Safety: Пиши хост-FTL на Rust. Его система типов и strict-границы не защищают от микроархитектурных уязвимостей процессора на 100%, но гарантируют отсутствие классических уязвимостей Out-of-bounds Read/Write, которые Spectre пытается использовать в качестве векторов атаки.

## Сравнение SPDK или tokio-uring на Rust

| Критерий | Intel SPDK (C / C++) | Rust + `tokio-uring` (io_uring) |
| :--- | :--- | :--- |
| **Архитектурный движок** | **Pure PMD (Poll Mode Driver)**. Полностью захватывает PCIe-устройство через `vfio-pci`. Поток ядра циклично опрашивает SQ/CQ очереди (100% утилизация CPU) в пространстве пользователя. | **Асинхронный ядерный Handshake**. Построен на базе интерфейса `io_uring` с флагами `IORING_SETUP_SQPOLL` / `IO_URING_OP_URING_CMD` (паспортный NVMe-пастру). |
| **Производительность & Задержки (Latency)** | Минимально возможная задержка (наносекунды). Переключение контекста в пространство ядра (Kernel-space) отсутствует полностью. | Идентична SPDK при включенном `SQPOLL`. Ядро Linux считывает NVMe-команды из общего кольцевого буфера без совершения системных вызовов (`syscall`). |
| **Энергоэффективность & Нагрузка на CPU** | **Низкая**. Одно или несколько ядер процессора жестко утилизированы на 100% круглосуточно, даже если на накопитель не поступает нагрузка. | **Высокая**. Асинхронные потоки `tokio-uring` эффективно засыпают (паркуются) при отсутствии I/O-операций и мгновенно просыпаются по прерываниям. |
| **Безопасность памяти (Memory Safety)** | **Низкая**. Требует ручной аллокации DMA-буферов (`spdk_dma_malloc`). Любая ошибка с указателем ведет к повреждению памяти или утечкам. | **Максимальная**. Гарантии компилятора Rust (ownership/borrow checker) полностью исключают Data Races, Use-After-Free и повреждение DMA-буферов. |
| **Сложность разработки хост-FTL** | **Высокая**. Требует написания сложной низкоуровневой обвязки на С для управления очередями, блокировками и стейт-машинами зон. | **Низкая**. Позволяет использовать всю мощь экосистемы Rust, async/await конструкций, а также безопасных коллекций для трекинга метаданных зон. |

*tokio-uring на Rust практически не уступает SPDK по скорости, но кардинально выигрывает в безопасности кода и экономии процессора хоста*.


# Как делать НЕ надо
Мы попытались скрестить ** зональную ZNS-логику кремния** с плоским, абсолютно не-ZNS блочным уровнем ядра Linux (/dev/nbd0).
В реальной индустрии так никто и никогда не делает, потому что:
1. Подсистема VFS ядра Linux считает любой стандартный блочный девайс обычной «плоской» флешкой или жестким диском.
2. Ядро начинает жить своей жизнью: при монтировании и переоткрытии файлов оно шлет фоновые скрытые запросы (Partition Scan, Flush, валидацию разметки), которые прилетали на случайные адреса.
3. Эти фоновые системные чихи ядра намертво взводили аппаратные триггеры ошибок (has_error, open_zones_count >= 4) внутри твоего zns_rules_checker.v еще до того, как наш Rust FTL успевал отправить боевые данные! В итоге мы боролись не со своими багами, а со скрытым поведением операционной системы.

# Как надо
Для тестирования и промышленной работы с ZNS SSD (например, в экосистемах NVMe ZNS, SPDK или LightNVM) ядро Linux полностью выкидывают из цепочки ввода-вывода (Bypass).

- Драйвер хоста (наш Host-FTL на Rust) общается с контроллером (твоим Verilator-кремнием) напрямую в User-Space через:
  -  сетевые RPC-протоколы, 
  - TCP-мосты или 
  - общую память (IPC).

- Это дает 0% системного шума, исключает ложные блокировки ядра и гарантирует, что аппаратура тактуется строго по командам FTL-драйвера.

# Стресс-тест
##  Многопоточный User-Space Стресс-Тест (Co-Simulation)

В проекте реализован сквозной многопоточный сценарий интеграционного тестирования, проверяющий потокобезопасность софтверного драйвера Host-FTL на Rust и стрессоустойчивость аппаратного ZNS-контроллера на Verilog (моделируемого через Verilator) в условиях конкурентной нагрузки.

### 📐 Архитектурная схема пайплайна

Тестирование полностью изолировано от блочного уровня ядра Linux (`/dev/nbd0`), что исключает фоновый системный шум (VFS Flush, Partition Scan) и обеспечивает кристально честную верификацию RTL-спецификации в User-Space:

### ⚙️ Алгоритм работы стресс теста

1. **Инициализация сокета**: Драйвер на Rust подключается напрямую к TCP-порту симулятора `10809`. Экземпляр драйвера инкапсулируется в контейнер атомарного подсчета ссылок и взаимной блокировки `Arc<Mutex<HostManagedFtl>>` для безопасного разделения сетевого дескриптора между потоками ОС.
2. **Превентивный Out-of-Band (OOB) сброс**: Перед стартом нагрузки хост отправляет команды очистки стартовых зон (0, 1, 2) через независимый Unix Domain Socket `/tmp/zns_mgmt.sock`. Это принудительно обнуляет триггеры ошибок и счетчик открытых зон внутри аппаратного модуля `zns_resources_tracker.v` на стороне кремния.
3. **Параллельный Append (Бомбардировка)**: Скрипт порождает 3 независимых системных потока (`std::thread::spawn`), имитирующих конкурентную запись от независимых приложений:
   * **Воркер 0** генерирует паттерн данных `0x01` и выполняет асинправный Append логической страницы **LBA 0** в **Зону 0**.
   * **Воркер 1** генерирует паттерн данных `0x02` и выполняет асинправный Append логической страницы **LBA 10** в **Зону 1**.
   * **Воркер 2** генерирует паттерн данных `0x03` и выполняет асинправный Append логической страницы **LBA 20** в **Зону 2**.
4. **Аппаратная валидация**: Запросы выстраиваются в очередь мьютексом сокета. C++ сервер принимает пакеты поочередно, выставляет порты `io_cmd = 1` и тактует конечный автомат Verilator. Кремниевый трекер ресурсов фиксирует одновременное открытие трех зон (`open_zones_count = 3`), проверяя жесткий лимит контроллера (`open_zones_count >= 4`).
5. **Побайтовая верификация**: После успешного Append-ответа от сокета каждый воркер захватывает канал, инициирует чтение записанной страницы через сохраненную таблицу трансляции адресов L2P (`logical_read`) и проверяет считанный массив байт на точное соответствие своей уникальной сигнатуре (`0x01`, `0x02` или `0x03`).

## 🔁 Тест циклического заполнения зон (Граничные условия RTL)

Интеграционный сценарий, верифицирующий граничное поведение конечного автомата (`zns_fsm_validator.v`) и логику автоматического освобождения ресурсов в трекере открытых зон (`zns_resources_tracker.v`) при достижении физического лимита емкости зоны в кремнии.

### 📐 Схема состояний зон и ресурсов контроллера

Тест моделирует последовательное заполнение накопителя, отслеживая триггеры переходов состояний ZNS-зон на аппаратном уровне:


### ⚙️ Алгоритм верификации граничных условий

1. **Параллельный старт**: Скрипт порождает 3 параллельных потока ОС ОС (`std::thread::spawn`), разделяющих один сетевой TCP-канал симулятора через `Arc<Mutex<HostManagedFtl>>`. Каждый воркер монопольно захватывает одну ZNS-зону (Воркер 0 -> Зона 0, Воркер 1 -> Зона 1, Воркер 2 -> Зона 2).
2. **Циклическая бомбардировка**: Каждый поток в цикле отправляет **ровно 64 последовательных Append-запроса** по 4 КБ каждый, полностью забивая физическую емкость зоны (суммарная нагрузка теста: 192 страницы / 768 КБ данных).
3. **Физика 63-й страницы (Терминальный такт)**: 
   * При фиксации транзакции на последней странице (`zone_wptr == 7'd63`), `zns_fsm_validator.v` в состоянии `ST_EXECUTE` аппаратно упаковывает в `bram_wdata` признак **`zone_is_full = 1`** (взводит 7-й бит структуры метаданных) и выставляет физический адрес `wptr = 64`.
   * Одновременно с этим, по внутреннему импульсу `state_update_pulse`, модуль `zns_resources_tracker.v` ловит терминальное состояние и выполняет автоматический декремент глобального счетчика открытых зон: `open_zones_count <= open_zones_count - 4'd1`.
4. **Пошаговый контроль целостности**: Сразу после завершения каждой асинправной записи хост выполняет пастру-чтение (`logical_read`) только что записанного сектора и побайтово валидирует сохраненную сигнатуру (Воркер 0 ищет `0x01`, Воркер 1 — `0x02`, Воркер 2 — `0x03`).

### ⚡ Инструкция по запуску

Тест выполняется в чистом user-space окружении без вовлечения драйверов блочного уровня ядра Linux.

1. Поднимите аппаратный TCP-сервер Verilator:
   ```bash
   make clean-nbd && make nbd-server
   |-- [NBD-Server] Ожидаем системного подключения ядра...
   ```
2. В соседнем окне запустите конвейер циклического заполнения:
   ```bash
   cargo run --release
   ```
